## Guides

Read the guide for the files you're editing:

- `packages/opui/components/AGENTS.md`: the Astro, Nunjucks, React, Solid, Svelte and Vue components and their type files.
- `scripts/AGENTS.md`: the example generator, its modules and the test behind each one.
- `src/component-api/AGENTS.md`: the `api.ts` data behind the API tables and anatomy diagrams.
- `src/docs/components/AGENTS.md`: the component docs pages and their examples.

## Workflows

- An example: write the `.astro` file in `src/component-examples/<slug>/`, run `pnpm build-examples`, commit the HTML, Nunjucks, React, Solid, Svelte and Vue files it writes.
- A block: write `src/blocks/<slug>/<Name>.astro` with the components, list it in `src/utils/blocks-data.ts`, run `pnpm build-examples`, commit the HTML, Nunjucks, React, Solid, Svelte and Vue files it writes. The block page shows the file of the visitor's framework.
- A component: write the `.astro` file, `types.ts` and `types.astro.ts`, declare a bound value as the `model` in its `api.ts`, then run `pnpm build-components`, which compiles the Nunjucks macro, the React, Solid, Svelte and Vue files and the four framework type files from them (`scripts/build-components.mjs`). When it refuses a construct it names it, with a code that `pnpm build-components --explain <code>` explains: support the construct, or list the files in `scripts/hand-written-components.json` with the reason and write them by hand with `/port-component <Name>` (`.claude/skills/port-component/SKILL.md`), which loops on the component tests until the four frameworks render the same markup.

## Characters

- Never write the em dash (U+2014) or the middle dot (U+00B7): `pnpm check-characters` fails on them in every tracked or new text file, and `scripts/check-commits.mjs` in commit messages and pull request titles.

## Colors

- Write every color as `oklch()`, relative colors too (`oklch(from var(--x) l c h / 50%)`): `pnpm check-colors` fails on any other syntax in every tracked or new file, except in comments, tests, `TODO.md`, generated files, released CHANGELOG entries and the `value` of `<input type="color">`.

## Sorting

Sort lists, arrays, query results and data displays in ascending order (lowest to highest, A-Ö, oldest to newest), unless their order carries meaning, such as a visual order, a reading order or a fixed key order.

## Comments

- Never remove comments unless asked to.
- Never add your own comments unless asked to do so. Only retain comments that are already present in the code.

## Typescript

- Prefer inference over explicit types.
- `pnpm lint` fails on `interface` and on annotations a literal already implies. Files that need declaration merging are listed in the `overrides` of `.oxlintrc.json`.
- No `enum`: `erasableSyntaxOnly` in `tsconfig.json` makes `pnpm typecheck` refuse one, and `tests/unit/typescript-config.test.ts` checks the option.

## Dependencies

- Never pin a dependency to an exact version: `tests/unit/dependencies.test.ts` fails on one in a `package.json` or the pnpm catalog.

## Commit messages

- Say what changed, not why.
- `scripts/check-commits.mjs` checks the prefix (`chore`, `docs`, `feat`, `fix`, `refactor` or `revert`), a subject of at most 100 characters and the forbidden characters. It runs as the `commit-msg` hook that `pnpm install` sets up, and on pull requests with their title.

## Changelog and What's new

- Log every user-facing change to the package in `packages/opui/CHANGELOG.md` under the unreleased version heading at the top, `## <version> - Unreleased` (`## 6.0.0 - Unreleased` now, dated by `scripts/release.mjs`), in `Breaking`, `Removed`, `Added`, `Changed` or `Fixed`.
- Entries describe the change since the last release. When you rework something already added or changed in the unreleased version, update that entry instead of adding a `Changed` or `Fixed` one.

- `tests/unit/migrating.test.ts` fails on a table row in `packages/opui/MIGRATING.md` that the Renames table on the release page can't read.
- For `Added`, `Breaking` and `Changed` entries, add or update a short note for the component page in `src/utils/whats-new.ts`. It renders the What's new callout on the page (a note that starts with `Breaking:` goes in the Migrating from 5.x callout instead). The sidebar's New badge is off for now; Bring the New badges back with 6.1 in `docs/releases/6.0.0-checklist.md` turns it back on. The components page lists a highlighted page under New components when the version adds the component and its slug is in `added` too, and under Updated components otherwise.
- Use `html`, `astro`, `react`, `solid`, `svelte` and `vue` keys when the notes differ per framework (classes vs props). A framework without a note gets no callout or badge.
- Link each note to the section on the page that documents the change (`<a href="#line">`). `tests/unit/whats-new.test.ts` fails on a note without a link and on a key that is no page, `pnpm check-dist` on a link to a missing id, and the type check on a `highlighted` slug with no notes.
- Keep the notes in sync when a change is reworked, and only remove notes when asked.

## Browser support

- Feature first. The library uses a new HTML or CSS feature as soon as one engine ships it, whichever engine that is, and waits for the others to catch up.
- A failure in one engine never gets a workaround in the component CSS. Mark it as an expected failure with its reason from `tests/e2e/engine-bugs.ts` (`failingIn` in `tests/e2e/stress-overlays.ts`, `failsIn()` elsewhere). `tests/e2e/engines.spec.ts` fails on a reason without a plain-HTML repro. When the browser catches up, the test fails with "expected to fail but passed": remove the entry.
- In the component CSS, a fallback is fine only when it costs nothing: an `@supports` block that turns a feature on, with the browser default as the fallback, or a declaration that changes no API and does nothing in the engines that have the feature (like the cap in the Menu's last-resort `@position-try` options). Vendor pseudo-elements that are the only way to style a native control (`::-moz-range-track`, `::-webkit-slider-thumb`) aren't workarounds.
- Any other fallback goes in the compat layer: `packages/opui/css/compat/<component>.css`, one `@layer components.compat` block, imported by `css/compat.css` in ascending order. Every rule sits in `@supports not (<feature>)` for a missing feature, or in an engine gate from `ENGINE_GATES` in `packages/opui/scripts/features.mjs` for a browser bug, with its repro in `tests/e2e/engines.spec.ts`. For an engine the e2e projects don't run (iOS), a `## To check` item in `TODO.md` gives the steps to check it by hand instead. List it in the Compat layer section of `src/docs/guide/browser-support.astro`, and update the engine lists in `tests/e2e/compat.spec.ts`. `tests/unit/compat.test.ts` fails once a fallback's feature is Baseline widely available: remove the fallback.
- `css/theme.css` and `core/normalize.css` load on every page and have no compat file, so each keeps a `@supports not (<feature>)` fallback next to the rule it completes. `coreFallbacks` in `packages/opui/scripts/features.mjs` finds those blocks, so the Baseline and no-compat bundles drop them like the compat layer's, and `tests/unit/compat.test.ts` holds them to the same rules.

## TODO.md

- `tests/unit/todo.test.ts` checks the format and lists the items that break it. Older items that break the headline rules are in `tests/unit/todo-allowlist.json`, which only shrinks.

## Testing

- A rule that a script or test enforces is written once, in the check's error message, and the guide keeps one line naming the check. Rules that need judgment stay in prose. `TODO.md` items with a `Replaces:` note name the prose a new check would shrink.
- Run `pnpm check` before finishing a change. It runs formatting, linting, CSS declaration order, `browserSupport` lists, component checks, custom property references, forbidden characters, color syntax, type checks, unit tests and the build, which ends by checking the links, anchors, ids, sitemap, Markdown versions, `llms.txt` entries, the domain redirect in `_redirects`, the Standard Site records the blog links and the relative imports of the modules the import map serves in `dist` (`pnpm check-dist`). `pnpm check:fast` runs everything except the build while iterating.
- `pnpm test:failed` reruns only the unit tests that failed in the last run. Don't use Vitest's `--sinceLastRun` or `--changed`: they only follow imports, and most unit tests read the files they check from disk, so an edit to a CSS file or a guide reruns nothing.
- Claude Code hooks in `.claude/settings.json` run `scripts/check-file.mjs` (forbidden characters, colors, declaration order) on each file an agent edits, plus the `TODO.md` and guide tests when it edits those files, and before a session stops also oxfmt, oxlint, Stylelint, the `TODO.md` and guide tests and `scripts/check-ratchets.mjs` on the files it changed since the upstream branch, and Knip when one of them is code, a `package.json` or `knip.json`. After editing through the shell, run `node scripts/check-file.mjs <files>`. The `pre-commit` git hook runs the same checks, oxfmt, oxlint and Stylelint on the staged files (`scripts/check-staged.mjs`).
- Component CSS (`packages/opui/css/components/`, `packages/opui/css/compat/`, `packages/opui/core/normalize.css`) reads `--ui-*` roles and its own `--_*` properties: `pnpm check-css-vars` fails on any other read unless `scripts/css-vars-allowlist.json` lists it, and the `history` CI job fails when an allowlist gains an entry (`scripts/check-ratchets.mjs`).
- The build regenerates the files listed in `scripts/generated-files.json`. Commit them. When they're stale on a pull request from this repository, CI commits the regenerated files to the branch and runs again; on `main` and on pull requests from forks it fails.
- `tests/unit/released-tokens.json` lists the theme tokens of the last published version. A token from it that disappears from `theme.css` fails the tests until a `Breaking` or `Removed` entry in the CHANGELOG names it. Regenerate it after a release with `pnpm test:record-released` on the tagged commit (see `RELEASING.md`).
- `tests/unit/released-api.json` lists the component props and CSS classes of the last published version. A prop that disappears fails the tests until a `Breaking` or `Removed` entry names both the component and the prop, and a class until one names the class. Regenerate it after a release with `node scripts/released-api.mjs <tag>` (the tag must exist locally).
- `tests/unit/scripts.test.ts` fails when a script in `scripts/`, `.claude/hooks/`, `.githooks/` or `packages/opui/` has no test that imports it or runs it by its path. `tests/unit/untested-scripts.json` lists the ones only their output can test, with the reason, and only shrinks (`scripts/check-ratchets.mjs`).
- A test that applies a rule to the repo's own files also feeds the rule a sample it must flag, since a broken rule passes a clean repo too.
- `tests/unit/instructions.test.ts` fails when a guide (`AGENTS.md` files, `.claude/agents`, `.claude/skills`) names a file, link or heading that doesn't exist, or cites a line past the end of a file.
- `tests/unit/framework-coverage.test.ts` fails when a framework in `src/utils/framework.js` has no renderer, compiler entry, barrel, package export, getting-started page, app, package fixture or type check, or is missing from an `import.meta.glob` pattern. The lists and patterns of frameworks and file extensions elsewhere derive from that file.
- `tests/unit/naming.test.ts` checks prop names, values and defaults against the naming model in `packages/opui/components/AGENTS.md`.
- `tests/unit/example-copy.test.ts` fails on placeholder copy in the Astro examples: Latin and filler ipsum, numbered and bare placeholder labels, short exclamations and text about the example. `tests/unit/example-copy-allowlist.json` lists the copy not yet rewritten and only shrinks (`scripts/check-ratchets.mjs`).

It guards the hand-written ports as much as the compiled ones.
- `tests/e2e/hydration.spec.ts` hydrates every React, Solid, Svelte and Vue example over its server markup, all the examples of a component in one page load (`?hydrate` on the fixture page, which renders each example with its framework's own server renderer and renders them on the client without it), and fails when hydration creates an element instead of claiming the server's, replaces or changes one, or changes the markup or form state. Its ledgers each give a reason: `LATE` for an attribute a script sets after hydration, `PROBES` for an element a framework builds and never inserts, and `KNOWN` for an example with a `TODO.md` item, which fails once the example hydrates cleanly. The interaction tests also run each case of those frameworks hydrated.
- `tests/e2e/models.spec.ts` runs the same scenarios in React, Solid, Svelte and Vue on a hand-written fixture per framework (`src/fixtures/models.*`, mounted by `src/fixtures/mount.ts` at `/dev/fixtures/<framework>-models/`), each with the framework's own idiom for state: what happens after the first render, which the markup tests can't see. A control keeps what the user entered when another prop changes, a select picks the child option its starting value names, a control follows its value and a form reset, a bound checkbox group keeps each value once through a form reset, a number field with a starting value can be emptied, a group handles a change nobody stores, and a list whose items are replaced by new objects keeps focus and the choice. Where a framework differs by design or has an open `TODO.md` item, the spec states its expected result with the reason (`ONE_WAY`), never a skip.
- `tests/e2e/updates.spec.ts` mounts every component in React, Solid, Svelte and Vue at `/dev/fixtures/<framework>-updates/` with the cases of `tests/unit/case-table.ts` and a set of native attributes, and fails when updating from no props and slots to a case, or back, renders other markup or form state than a fresh render of the result.
- `tests/e2e/native.spec.ts` renders each framework's native comparison pair (`tests/apps/native/`) on the server at `/dev/fixtures/<framework>-native/`, changes every control before hydration (`?hold`, released by a `hydrate-native` event), and checks the cases in `tests/apps/native/cases.ts` without building an app. `pnpm test:apps` runs the same cases in every hydrated app. Each lists the differences it expects with their reason.
- `tests/e2e/example-display.spec.ts` checks the display model in `scripts/example-display.mjs` against the browser: the computed `display`, `white-space` and generated content of every element in every HTML example.
- `pnpm test:apps` builds the packed package into Eleventy, Next.js, Nuxt, SvelteKit and the Vite starters for React, Solid, Svelte and Vue (`tests/apps`, its own pnpm workspace), renders every example (and in Eleventy every block, with the setup the Nunjucks getting-started page gives) on the server and in Chromium, and fails on a missing example, a console error or warning such as a hydration mismatch, an undefined `opui-*` element or CSS that doesn't load. Its scenarios also change form controls before the page hydrates and expect them kept, load every element before React hydrates (`/elements-first/` in Next.js), come back to a page the browser restores, reset a form after hydration, and run React's StrictMode on the Vite dev server (`vite-react-dev`), and it builds Next.js, Nuxt, SvelteKit and the Vite Svelte starter again with the `light-dark()` settings that `tests/package/readme.ts` reads from the package README. CI runs it on its own when `packages/opui`, the examples, the blocks or `tests/apps` change; run it (`OPUI_APPS=<app>` for one app) to debug a red `apps` job. `tests/unit/app-coverage.test.ts` fails when no example imports a component.
- `pnpm reference prepare` and `pnpm reference test` build the packed package into one small app, a feed, chat, photos, a profile and settings, written by hand in Astro, Eleventy, SvelteKit, Next, Nuxt and Solid 2 (`tests/reference`, its own pnpm workspace), and run one Playwright suite against all six: how the components compose, client navigation, a second theme, phone layouts, axe and console errors. Solid is plain Solid 2 with `@solidjs/vite-plugin`, not SolidStart. `tests/reference/README.md` is the contract every app follows and says how to add a screen. A library bug the suite hits is listed in `tests/reference/spec/known.ts` as an expected failure, never worked around in an app. `pnpm reference dev` starts all six apps and an index page to click around in. CI runs it in the `reference` job when `packages/opui` or `tests/reference` change, and before Publish. `tests/unit/reference-coverage.test.ts` fails when an app misses a screen or a screen has no spec.
- NEVER update snapshots to make a failing test pass unless the change is intended, and say so in the commit message when you do. The `history` CI job fails when `tests/e2e/a11y-known-violations.json` or the parity `.diff` files gain an entry (`scripts/check-ratchets.mjs`).
- Re-record intended drift with `pnpm test:record-drift` and violations with `pnpm test:e2e:record-a11y`. The tests fail on a `.diff` file or ledger entry that no longer applies.
- Visual baselines are only generated in CI. Add the `update-snapshots` label to a PR to regenerate them. Never commit screenshots generated locally: the `history` CI job fails when a baseline was last committed by anyone but the bot, and `tests/unit/screenshots.test.ts` fails on a baseline that belongs to no example, block or theme.
