# Releasing

The steps every release of `opui-css` repeats. The one-off checks of a major release live in `docs/releases/`, for example [`docs/releases/6.0.0.md`](docs/releases/6.0.0.md).

The package has one version, `version` in `packages/opui/package.json`. The home page shows it and the CDN links in the docs point at its major (`opui-css@6`). The docs deploy from `main` on every push, independently of releases, so `src/utils/release.ts` compares the version with the last published one, `version` in `tests/unit/released-api.json`: while it is newer and the CHANGELOG doesn't date it, the home page marks it as not on npm yet, and the pages with CDN links say how to get the files meanwhile. A bump can land on `main` ahead of the release. The root `package.json` is private and has no version, and the docs site has no changelog of its own: `packages/opui/CHANGELOG.md` is the changelog.

## Before

1. CI is green on `main`, both jobs (`check` and `e2e`), with everything the release ships merged.
2. `packages/opui/CHANGELOG.md` starts with `## <version> - Unreleased`, and every `Added`, `Breaking` and `Changed` entry has a What's new note (see `AGENTS.md`).
3. The local `main` is clean and up to date with `origin/main`.

## Release candidate

A major release, or any release worth trying in a real project first, starts with a release candidate:

```bash
node scripts/release.mjs 6.0.0-rc.1
```

`node scripts/release.mjs prerelease` (`pnpm release:prerelease` in `packages/opui`) picks the next one: `6.0.0-rc.1` while `package.json` says `6.0.0` and the CHANGELOG has `## 6.0.0 - Unreleased`, then `6.0.0-rc.2` and so on. The script runs the same steps as a release (below), except that it leaves `## 6.0.0 - Unreleased` undated and publishes to the `next` dist-tag instead of `latest`, so `npm install opui-css` and `opui-css@6` on the CDN keep the last release. Try the candidate with:

```bash
npm install opui-css@next
```

```html
<link
  rel="stylesheet"
  href="https://cdn.jsdelivr.net/npm/opui-css@next/dist/opui.css"
/>
```

The home page shows the candidate's version and marks it as a release candidate. Fixes go through pull requests as usual, and each new candidate is another `prerelease` run. When the candidate holds, release the version itself.

## Publish

Run the release script from the repository root with the version to publish:

```bash
node scripts/release.mjs 6.0.0
```

It stops if the branch isn't `main`, the working tree isn't clean, the tag exists or the CHANGELOG has no `## <version> - Unreleased` heading (for a candidate, the heading of the version it leads to). Then, in order, it:

1. dates the heading, `## <version> - Unreleased` becomes `## <version> - YYYY-MM-DD` (not for a candidate),
2. sets `version` in `packages/opui/package.json`,
3. runs `pnpm check`,
4. commits everything as `chore: release <version>`,
5. publishes with `pnpm publish --tag latest` from `packages/opui`, or `--tag next` for a candidate (`prepack` builds `dist`),
6. tags the commit `<version>`, without a `v` prefix like the existing `5.4.3`,
7. pushes `main` with `--follow-tags`.

CI builds `main` and deploys the docs. The dated heading tells `src/utils/release.ts` that the version is out, so the docs stop marking it as unreleased with the release commit. `pnpm release`, `pnpm release:minor` and `pnpm release:major` in `packages/opui` call the script with the next patch, minor or major version computed from `package.json` (from `6.0.0-rc.2`, each of them gives `6.0.0`); pass the version yourself when `package.json` was bumped ahead of the release.

The publish runs on your machine, so it has no provenance statement: npm only signs provenance for a publish from CI, which is in `TODO.md`.

If the publish fails, the release commit is local and nothing is tagged or pushed. Fix the cause and run the script again after `git reset --hard origin/main`.

## After

1. `https://cdn.jsdelivr.net/npm/opui-css@<major>/dist/opui.css` resolves (`curl -sI`), the docs deploy from `main` and the home page shows the version.
2. Write the GitHub release from the tag: the `Breaking` section of the CHANGELOG and a link to `MIGRATING.md`.
3. The next change to the package starts a new `## <version> - Unreleased` section at the top of the CHANGELOG.
4. The released guards are regenerated by the `After release` workflow (`.github/workflows/after-release.yml`). On the push of a release tag (`6.0.0`, not a candidate), it checks out the tagged commit, runs `node scripts/released-api.mjs <version>` and `pnpm test:record-released`, pushes the result to `chore/released-<version>` and opens a pull request against `main`. If the repository doesn't let GitHub Actions open pull requests, the run summary links the compare page to open it from instead. CI doesn't start on its own for a branch that Actions pushed, so run the `CI` workflow on the branch from the Actions tab before merging.

   By hand, on the tagged commit:

   ```bash
   git checkout <version>
   node scripts/released-api.mjs <version>
   pnpm test:record-released
   ```

   `released-api.mjs` reads the tag with `git archive`, so it must exist locally (`git fetch origin tag <version> --no-tags`). `test:record-released` writes `tests/unit/released-tokens.json` from the current `theme.css` and `packages/opui/package.json`.
